# Setup

**Write scope:** report and proposed text only until explicit approval. After approval, only the approved instruction edits on a `chore/dev-setup` worktree, one commit and a PR. Never edit the default branch directly, push directly to it or merge. No change lifecycle or tracker writes.

1. Establish the target repository, its default branch and ownership from the remote and authenticated repository metadata; do not infer ownership from the checkout path or assume a fork's upstream belongs to the user. Fetch `origin refs/heads/<default>` and read `git show FETCH_HEAD:AGENTS.md`. If fetching fails, stop with unknown authority; never substitute the edited local file. A successful fetch with no `AGENTS.md` means the file is missing; other read failures are unknown and stop the audit.
2. Report each dev input as **present**, **missing** or **ambiguous**: Tracker and board; Layers; Pull requests (title style, labels, project); Merge policy; Testing (the local checks completion runs before publishing); real-device permission when the repository drives hardware; named verification skill. Mark hardware permission not applicable for a non-hardware repo, with the evidence for that conclusion. Absence of permission never grants it. Do not change existing sections, even ambiguous ones, without explicit approval.
3. Draft missing sections from repository facts: remote/ownership metadata, `gh label list`, `.github/workflows/`, branch protection and existing project instructions. Show the text and what was verified versus unknown; do not invent a tracker, board, labels, project, policy or commands. An unresolved fact stays a question in the report, never an operative instruction. The draft is text in the report, not an edited file or worktree. A complete repository ends with a report, no empty PR.
4. Once per setup interaction, only for a repository established as the user's own, offer one concrete task line naming the bare `verify-change` skill and this repository's verified verification facts (for example, “Before verifying the running app, load verify-change.”). Show the proposed facts alongside it; do not activate the line without approval. For a third-party repository, report that such a line would select nothing; do not offer it. If ownership or verification facts are unknown, establish them or report unknown. Remember an accepted or declined offer within the interaction and do not repeat it.
5. Show the complete proposed edit and obtain explicit approval, including any existing section to change. No answer or rejection leaves a report only. On approval, use a clean `chore/dev-setup` worktree (`wt switch --create chore/dev-setup --no-cd`); if the branch already exists, inspect and report rather than overwriting it. Apply only the approved sections, keeping all real instructions in `AGENTS.md` and `CLAUDE.md` as its import. Run the repository's documented checks; unknown required conventions stop publication. Make one commit, then use the github skill's pull-request reference for the PR, including repository labels and project conventions. Push only this work branch for that PR, never directly to default. Read the PR back to verify it; report the URL and stop. Do not enter `lifecycle.md` or merge.
