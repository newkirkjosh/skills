# Host adapters

Read this before the first spawn when the coordinator runs on a host other than Claude Code, or in a headless session; `completion.md`, `team` and `cross-review` point here for the same waits. `dev`'s lifecycle steps in `lifecycle.md` are written as operations; the example syntax in `SKILL.md` is Claude Code's. Adapted from fx/skills `dev/references/host-adapters.md` (see `LICENSE.txt`); Codex lifecycle behavior depends on the session’s supplied tools, not the CLI version alone. Inspect and probe those tools before relying on stop or capacity semantics. The current hosted interface is documented at https://developers.openai.com/api/docs/guides/responses-multi-agent; a different backend must prove its own lifecycle.

## Operations

| Operation | Claude Code | Codex |
|---|---|---|
| Delegate | `Agent` tool: `subagent_type`, `model` (tier), `prompt`, `run_in_background` | `spawn_agent`: `task_name`, `message`, `fork_turns: "none"`, `model`, `reasoning_effort` |
| Give the delegate its role | The prompt names the role file by absolute path | Same; there is no `Skill` tool, the child reads the file |
| Wait for a delegate | Its completion notification wakes you; never poll | `wait_agent` with a `timeout_ms` (milliseconds) worth several minutes, e.g. `600000`, **before your turn ends** |
| Correct a running delegate | `SendMessage` | `send_message`, or `followup_task` to make it act |
| Continue a finished delegate | `SendMessage` to its agent ID: it resumes in the background with its context, and its next final message arrives as a completion | `followup_task` |
| Run a long command | `Bash` with `run_in_background: true` into a log; read it on the notification | Use the native long-command execution and continuation tools; keep waiting on the returned session until its terminal result |
| Cross-model reviewer (`cross-review`) | `codex` | `claude` |
| Stop a running delegate | `TaskStop` | `interrupt_agent`, then `list_agents` to verify status; legacy backends may expose `close_agent` instead (see below) |
| Instructions the host reads | `CLAUDE.md` (which imports `AGENTS.md`) | `AGENTS.md` only; never `CLAUDE.md` or `REVIEW.md` |
| Skills directory | `~/.claude/skills` | `~/.agents/skills` |

## Background permission results

Inspect the operation's actual result; a permission request does not prove that a prompt is waiting. In an observed Claude Code background worker, a forced permission ask for PR creation was rejected immediately because there was “no active turn”; the worker returned `BLOCKED unavailable`. That result ends the attempted operation: preserve its denial reason and report `BLOCKED` (under `team`, the invocation's `TEAM: BLOCKED unavailable: <operation and reason> #<i>`). Do not wait 30 minutes for an answer, retry the operation, or widen permissions to work around it. Retire outstanding roles and processes through the normal completion/stop rules before the final handoff; a rejected operation alone does not prove the worker or its roles stopped.

Use the unanswered-prompt path only when the current host and delegation path have verified that a prompt remains waiting, and the request is observed pending. Inform the user and never answer it for another agent; `team` applies its 30-minute unanswered-prompt deadline. The Claude Code rejection observation establishes no waiting host. On an unverified host, behavior remains unknown: do not infer either a waiting prompt or automatic rejection from the host name or idle output. Record the missing evidence and report the capability unavailable if required work cannot proceed.

## Claude Code completion and stopping

Record each nested role’s agent/task ID when it starts. A normal handoff includes every role ID, its terminal completion notification or task result, and any owned process cleanup. Correlate terminal evidence with the exact ID; prose saying “finished”, a quiet output file or a parent’s completion alone proves nothing about its descendants.

When stopping, apply `TaskStop` to each known active task that the host lets the caller address, including descendants, and retain the returned per-ID stop confirmation. A completion notification for that same ID also establishes a terminal state. Do not assume stopping a coordinator recursively stops its roles, invent a nested-status API, or infer a stop from a failed lookup. The supervisor uses the worker’s ID/evidence inventory and the host’s actual task results; if descendant IDs or terminal evidence were never exposed, keep `stop unconfirmed` and report what the user must inspect. Verify launched processes separately. A verified stop releases proven capacity; it never substitutes for a successful evaluator or a valid lifecycle handoff.

## Codex gotchas

- **Wait before ending a native run.** Use `wait_agent` on outstanding native children before the final response; whether ending a turn preserves them is host-dependent. A host-managed background delegate can have a different wait contract: follow the tool’s returned instructions, including yielding when completion will wake the session. Do not transfer that exception to native children or one-shot processes.
- **`fork_turns: "none"` or no tier.** Omitted (or `"all"`), the child forks your whole history and inherits your model and effort, and the host rejects a `model` or `reasoning_effort` override. With `"none"` the child sees only `message`, so the Scope Brief and the role file path go in it verbatim.
- **Tiers map onto model plus effort.** Codex offers fewer general-purpose coding models than three tiers, so: `large` is the stronger model at `high`, `medium` the same model at `medium`, `small` the faster model at `low`. Resolve the names from the host at run time, never from this file.
- **Capacity is a live-work limit on current backends.** Retained completed contexts need not occupy capacity: the hosted collaboration interface limits active turns. Keep `team` at one Codex worker at a time so nested roles have room, and prove sequential capacity reuse in preflight rather than assuming a numeric lifetime limit. A legacy backend may instead require `close_agent` to release capacity; use it only when supplied and required by that backend. Never call an absent tool or assume interruption deletes a context.
- **Stopping and finalizing are different.** On the current interface, a successful role report plus a terminal tool result or observed `completed` status establishes completion; do not interrupt completed agents just to retire them. To stop active work, interrupt each known running worker and descendant separately, then verify every known agent is `completed` or `interrupted` through `list_agents` or a recorded terminal tool result. Retain those observations when a host stops listing completed contexts; absence from a listing alone is not proof of stopping. On a legacy backend without listing, require explicit close confirmation for each known agent instead. An interrupt of a coordinator does not prove its descendants stopped, and it does not kill shell processes already launched: verify those separately. Unknown or still-running work stays `stop unconfirmed`. Preserve agent IDs for deliberate `followup_task` continuation; never resume a held worker.
- **`task_name` takes only lowercase letters, digits and underscores.** `test-author-ui` is rejected; write `test_author_ui`.
- **Delegation must be asked for in words.** Codex suppresses sub-agents unless the instructions explicitly ask for sub-agents or delegation, so when running `dev` under Codex, spawn sub-agents for the three roles as written; a child that should fan out must be told to in its `message`.
- **One shared working directory, no isolation flag.** Every child runs in the same filesystem. `dev` already runs each change in its own worktree; pass that absolute path in every `message` and tell the child to `cd` there on every command.
- **`claude -p` needs the network.** Under a sandbox that blocks it, the cross-model review fails with a connection error, not a review. Before escalating, confirm the worktree holds no secrets: the script sends the diff and the Scope Brief to the other model, which can read any file in the worktree. Then run the `cross-review` skill's `cross-review.sh` with the host's escalated permission rather than skipping the review.

## Headless sessions

A run is headless when nothing can answer or wake it mid-run: a one-shot `claude -p` or `codex exec`, a scheduled job, or any session whose process ends with its turn. If you can't tell, treat it as headless: waiting in the foreground on an interactive host costs idle time, while ending the turn on a headless one silently skips every gate still ahead.

- **Never end the turn while a wait is outstanding**: a subagent, a review, or a CI or CodeRabbit waiter. Nothing will wake you to read it.
- **Run waiters in the foreground**, inside the host's foreground limit (under 10 minutes for a Claude Code `Bash` call): pass a shorter timeout (for example 7 minutes) to the bounded helpers documented in the `github` skill's pr-evidence.md. Set the execution tool's own timeout above the helper budget plus API/collection overhead, within the host limit (for example Claude Code `Bash` `timeout: 600000` for a 7-minute waiter); its default timeout is too short. If the command is killed or returns no verdict, evidence is unavailable and merging stays blocked; never infer PASS. On exit 3, relaunch only within the remaining overall wait budget; carry the returned `wait_after_run` into `WAIT_AFTER_RUN` (including clearing it when empty). Never reset the overall budget; native host wait/monitoring rules override fallback waiters.
- **Spawn subagents in the foreground** (on Claude Code, without `run_in_background`), so the call returns their report. A Claude Code session that is itself a background agent (a `team` worker) may get its spawns back asynchronously anyway: the call returns at once and the report arrives later as a completion notification. That role is still outstanding: wait for its notification before the next step that needs its report. If Claude Code requires ending the current turn to receive the notification, yield with an interim message naming the outstanding role; this is a suspended invocation, not its final report. Resume on the role completion, without spawning a replacement. Only deliver the invocation’s final report after every role has reported. A true one-shot process that cannot resume must use a blocking wait or report the capability unavailable; yielding cannot make that process resumable.
- **No questions mid-run.** Where the workflow would stop to ask the user, finish everything the question doesn't block, then put the question in the final report.
- **Polling is still forbidden.** Prefer native host monitoring; fallback waiter invocation follows the `github` skill's pr-evidence.md.
